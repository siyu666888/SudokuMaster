**工程性**
- 纯离线单机，仅 `VIBRATE` 权限；R8 混淆 + 资源压缩；自签名 release 并校验交付

## 3. 主要挑战与限制

### 3.1 工程与流程（最高风险）
1. **无版本控制**：工程不是 Git 仓库 —— 无变更历史、无法回滚、无法做 Code Review 与分支开发；`keystore/` 与 `keystore.properties`（含密钥口令）目前无任何忽略规则保护，一旦初始化 Git 且未配 `.gitignore` 就会泄露。
2. **Gradle 版本不一致**：wrapper 声明 8.9，本机构建用 8.7；8.9 组合**从未验证**，他人/CI 用 wrapper 构建可能失败。
3. **零测试**：纯 Kotlin 的 `domain`（1018 行：生成/求解/评分/统计/状态机）完全无单测覆盖；每次算法或统计改动只能靠手工验证。
4. **无 CI**：构建、Lint、签名校验、APK 归档全靠手工命令。

### 3.2 架构
5. **分层边界有污染**：`domain/session/GameSession` 直接 import `data.entity.SavedGameEntity`（domain 依赖 data）；`GameSession` 内部直接调 `System.currentTimeMillis()`，时间与状态耦合，难以注入测试。
6. **导航靠字符串拼接**：`Routes.GAME_PATTERN` 携带 `puzzle`/`solution` 明文拼在路由里（`game?...&puzzle=81位数字`），无编译期类型校验，参数增多后易错。
7. **状态派生冗余**：`AchievementsViewModel` 从同一个 Room Flow 派生 6 个 `StateFlow`（total/hell/best/lastPlayed/overview/groupStats/rows = 7 个），每次数据变化重复遍历全表。

### 3.3 性能
8. **生成算法开销**：每个挖洞都跑一次完整 `countSolutions`，且 `fillGrid` 每步 `indexOf(0)` 线性扫描；9×9 在低端机上明显，当前靠 `fastGen`（多留 20% 线索）绕开，属于"降质换速"。
9. **每次开局都要生成**：无题库缓存/预生成，冷启动开局等待。
10. **胜利结算全表扫描**：`handleWin` 用 `allRecords().first()` 载入全部记录再 `minOf` 求最佳，应下推到 SQL。
11. **无 Baseline Profile / 启动测量**：Compose 首帧与滚动性能未做基线优化。

### 3.4 产品与合规
12. **单存档槽**：只有一条 `saved_game`（id=1），开新局/导入/复玩会**静默覆盖**进行中的进度，无任何确认提示。
13. **国际化与无障碍缺失**：全部文案硬编码中文（`strings.xml` 仅 1 项）；大量 Icon 的 `contentDescription = null`，TalkBack 不可用；`supportsRtl=true` 但未做 RTL 验证。
14. **图标非自适应**：只有 mipmap PNG，无 `ic_launcher.xml` 自适应/单色图标，Android 13+ 主题图标不支持。
15. **混淆规则过宽**：`-keep class androidx.compose.runtime.** { *; }` 与全局 `-dontwarn` 会削弱 R8 收缩并掩盖真实问题。
16. **数据备份依赖剪贴板**：备份只能复制到剪贴板，无法导出为文件（换机场景下体验差）。

## 4. 改进方案

> 成本刻度：低 = 0.5 人日内；中 = 0.5–2 人日；高 = 2 人日以上或需专项验证。
> 收益刻度：高 / 中 / 低。优先级：P0 必须做 · P1 建议做 · P2 可选。

### 4.1 工程基础（P0）

| # | 建议 | 具体做法 | 预期收益 | 成本 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| E1 | 纳入版本控制 | `git init` + 写 `.gitignore`（忽略 `keystore/`、`keystore.properties`、`app/build/`、`release/*.apk`、`.gradle/`），首次提交后即建立回滚点 | 高（可回滚/可协作，杜绝密钥入库） | 低 | **P0** |
| E2 | 统一 Gradle 版本 | 把 wrapper 改为本机已验证的 8.7（或本机升级到 8.9 并验证一次构建），二选一，禁止长期并存 | 中（消除"他人构建失败"隐患） | 低 | **P0** |
| E3 | 建立最小 CI | 一个脚本或 GitHub Actions：`gradlew lint assembleRelease` + `apksigner verify` + 产物归档到 `release/` | 高（每次改动自动验证，避免"能编译但装不上"） | 中 | **P1** |
| E4 | 补齐 domain 单测 | 为 `SudokuEngine`（生成唯一解/求解）、`ScoreCalculator`（星级/评级边界）、`StatsAnalyzer`（连续天数跨月/断档/空列表）、`GameSession`（撤销重做/暂停计时/自动排除）写 JUnit 测试 | 高（回归安全网，支撑后续算法优化） | 中 | **P0** |

> E4 前置：为 `GameSession` 注入时间源（见 A1），否则计时相关用例不可测。

### 4.2 功能优先级

| # | 建议 | 具体做法 | 预期收益 | 成本 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| F1 | 覆盖存档前确认 + 多存档 | 开新局/复玩/导入前若存在进行中局，弹确认框；中期把 `saved_game` 改为按 `id` 多槽（每个 size:diff 一局） | 高（消除静默丢进度的核心体验缺陷） | 中 | **P0** |

| F3 | 题库缓存与预生成 | 后台按 `size:diff` 预生成 3–5 题写入 `puzzles` 表，开局直接取；无缓存时再同步生成 | 高（开局几乎无等待） | 中 | **P1** |

### 4.3 架构优化

| # | 建议 | 具体做法 | 预期收益 | 成本 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| A1 | 解除 domain→data 依赖 | 抽出 `GameSnapshot` DTO（sizeId/diffId/values/given/notes/elapsed…），`GameSession` 只认 DTO，`SavedGameEntity ↔ DTO` 映射放在 data 层；同时注入 `Clock`（`fun now(): Long`）替代裸 `currentTimeMillis()` | 高（domain 真正可单测，分层可维护） | 中 | **P1** |
| A2 | 导航类型安全 | 升级 Navigation 2.8.x，用 `@Serializable` data class 定义路由（含 `newGame/replay/import`），删除字符串拼接 | 中（编译期校验，杜绝参数拼错） | 中 | **P1** |
| A3 | 合并成就页状态派生 | 把 7 个 `StateFlow` 收敛为 1 个 `AchievementsUiState`（data class），VM 内部一次遍历算完；UI 只订阅一个状态 | 中（减少重复遍历与重组） | 低 | **P1** |
| A4 | 版本与依赖集中管理 | 引入 `libs.versions.toml`（Version Catalog），版本/产物名集中一处 | 中（升级时改动面可控） | 低 | **P2** |
| A5 | 保留自建 DI | 不自引入 Hilt；`AppContainer` 规模匹配当前体量，如需构造参数再局部补工厂 | 低（避免为小项目增加构建复杂度） | 低 | — |

### 4.4 性能提升

| # | 建议 | 具体做法 | 预期收益 | 成本 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| P1 | 生成算法优化 | `fillGrid` 改用 MRV（最少候选优先）选格 + 位掩码记录行列宫占用，避免每步 `indexOf(0)` 与重复扫描；保留唯一解校验 | 高（9×9 生成显著加速，可下调/移除 `fastGen` 的降质） | 中 | **P1** |
| P2 | 结算聚合下推 SQL | `GameRecordDao` 增加 `@Query("SELECT MIN(timeMs) FROM game_records WHERE sizeId=:s AND diffId=:d")`，替换 `handleWin` 的全表载入 | 中（胜利结算不再随记录数变慢） | 低 | **P1** |
| P3 | Baseline Profile | 新增 `:baselineprofile` 模块 + Macrobenchmark，生成启动/成就页滚动基线 profile | 中（首帧与滚动提速，Compose 收益明显） | 高 | **P2** |

| P5 | 重组优化 | 成就墙/历史列表为 `items` 提供稳定 `key`（历史已有）；`rows` 用 `ImmutableList`/`remember` 缓存分组结果 | 低–中（滚动顺滑） | 低 | **P2** |

## 6. 建议路线图

**阶段一：工程地基（1–2 天）**
`E1 版本控制` → `E2 Gradle 统一` → `D1 迁移兜底` → `P4 混淆规则` → `E4 domain 单测`
目标：让项目"可回滚、可验证、可回归"，后续所有改动有安全网。

**阶段二：体验与正确性（2–4 天）**
`F1 覆盖确认/多存档` → `A1 分层解耦+时钟注入` → `A3 状态收敛` → `P2 SQL 聚合` → `F5 无障碍`
目标：消除"静默丢进度"等真实缺陷，让核心链路可测。

**阶段三：性能与现代化（3–5 天）**
`D2/D3 工具链升级（Kotlin 2.x + KSP + 新 BOM）` → `P1 生成算法` → `F3 题库缓存` → `A2 类型安全导航` → `E3 CI`
目标：开局体验与长期可维护性上一个台阶；**每步升级后必须完整回归一次**。

**阶段四（可选）：增长与扩展**
`F4 每日挑战`、`F2 文件备份`、`P3 Baseline Profile`、`F7 多语言`、`F6 自适应图标`。

## 7. 暂不建议投入的事项

1. **引入 Hilt / Koin**：当前 `AppContainer` 足够，新增框架只会增加构建复杂度与学习成本。
2. **引入网络/账号/云同步**：项目定位是"纯离线单机、不收集数据"，这是明确的差异化优势，不应破坏。
3. **为 UI 铺开 Compose UI 测试**：在 domain 单测未建立、工具链未升级前，UI 测试维护成本高于收益；先补 domain 层。
4. **过早做模块化拆分**（如拆成 `:core` / `:feature:*`）：6524 行单模块 + 已验证的构建链，拆分收益不明显，反而拖慢迭代。
5. **把难度色改成随主题变化**：难度色是全局语义色（首页/历史/成就三处一致），随主题变化会破坏"颜色=难度"的认知。

## 8. 关键风险提示

- **工具链升级（D3）必须单独成批并全量回归**：Kotlin 2.x + Compose Compiler 变更涉及编译插件，与 R8、kapt/KSP 有耦合，建议先建 CI（E3）再升级。
- **移除 `fallbackToDestructiveMigration`（D1）前**必须确保 `MIGRATION_1_2` 已覆盖所有存量版本路径，否则老用户升级会崩溃（而非静默清库）。
- **`keystore/` 与 `keystore.properties`**：仅在本地保留；一旦初始化 Git，`.gitignore` 必须先于首次提交落地。
